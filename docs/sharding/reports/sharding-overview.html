The problem

hogdb was one process holding all of state

Balances, auth data, contract data, retrocausal queues, wasm code, hog ages — all of it in a single hogdb. That process is the memory and write-bandwidth ceiling for the whole validator.

The complication is that three independent subsystems talk to hogdb directly, each with its own concurrency model: the mempool scheduler (async, coroutine RPC), hogexec's DatabaseProxy (synchronous, per-transaction), and the auth server (async, subscription-driven). Before this work they shared no code for talking to the database. "Just add a shard" therefore means changing three client paths at once — and if any two of them disagree about which shard owns an address, the write lands on one shard and the read asks another. There is no error. You get Not Found, which most call sites read as "no such account."

A read must repeat the routing its write used. Every other decision in this design is a consequence of that one sentence. The three ways to break it — different code, different hash version, right code pointed at the wrong socket — each got its own mechanism, and each shipped after a real bug.

What shipped

One routing rule, three client paths

The core of the change is a new module, hogd/db_shard_routing/: two headers that own key placement, batch splitting, and concurrent fan-out. Every subsystem now goes through it rather than holding its own database client.

Key placement

Everything an account owns lands on one shard

Balances, auth data, contract data, retrocausal queues, and hog ages all route on the address — contract data ignores the key field deliberately, so a single-account transaction touches a single shard. Wasm code is content-addressed to shard 0; db tip and cost model are replicated to every shard.

Block hash

Partial hashes that sum

Each shard hashes only its own items. Because these are LtHash16 multiset values they are additive, so the partials sum to exactly the unsharded hash. The block header therefore does not depend on how many shards a validator runs — a 1-shard and a 4-shard validator produce byte-identical headers, with no protocol change.

Shard identity

A shard knows which shard it is

--shard-id / --total-shards, persisted in a metadata record excluded from the consensus hash. The persisted record is authoritative and flags may only confirm it; relabelling a populated database is fail-stop. Identity travels to clients on the ShardCard, and clients bind by declared id, never by connection-arrival order.

Fan-out discipline

Launch all, drain before rethrowing, visit every shard

All shard calls are issued before any is awaited, so N shards cost one round trip. A throw mid-gather drains its siblings first — abandoning a running x23::Async is a use-after-free. And no fan-out ever early-returns: stopping partway through a commit leaves some shards committed and others only prepared, which abort cannot undo.

Zero copy

Batch splitting that doesn't duplicate 250 MB

notify_vetted batches reach ~250 MB. Rather than materialize per-shard sub-batches, the split records only per-shard index vectors plus a borrow of the source, and a gather view serializes the source items in place through an x23 serialize_equiv specialization.

Control plane

Replicated globals, with agreement required

Every shard runs the whole block lifecycle against its own globals. Writes go to all; reads require unanimity — get_tip fail-stops on partial genesis or any tip mismatch. That is the validator-startup detector for a crash mid-commit-fan-out. Loud beats livelock.

How it went

Five phases, June to August

  1. Phase 1Jun 29 – Jul 9

    Make the executor shard-shaped, then extract the layer

    Reshaped hogexec's single database client into a per-shard array, turned on per-key routing, and made writes a two-phase fan-out across shards. Then pulled the routing, splitting, and gathering out into db_shard_routing so the mempool and auth could share it instead of reimplementing it.

  2. Phase 2Jul 16 – Jul 24

    First 2-shard cluster runs — and the block-0 stall

    The first multi-shard run stalled at block 0 with a mempool SIGSEGV. Root cause was a genesis-delta ordering race: the scheduler read hog ages routed to shards that hadn't loaded genesis yet. Fixed with a genesis-readiness barrier. By July 24 a 2-shard run completed all 1,000 work batches — ~39.9M txs at ~18,000 tx/s — with the new coordinator-failure guard catching the exact condition that had previously killed the process.

  3. Phase 3Jul 27 – Aug 4

    Correctness hardening, and the silent auth stall

    Shard identity end-to-end, fail-stop on divergent tips, a per-block transfer barrier, shard-owner-only genesis with a global header hash, and golden values pinning the address→shard map. Removing replicated genesis then exposed a latent bug: the auth server was bound to a single shard, so it could only see half the accounts. The symptom was 16,945 empty blocks in 28 minutes — height climbing fast, no crash, nothing in any log. Fixed with routed reads, subscription fan-out, and per-height key-change aggregation.

  4. Phase 4Aug 3 – Aug 4

    Review, tests, and a validated run

    Six review rounds; five fan-out bugs fixed in one pass (including the drain-before-rethrow use-after-free, found in review rather than testing). 31 targeted tests across five new suites, plus CI format and tidy clean. The August 4 cluster run committed 79,490,644 transactions across 343 non-empty blocks with the two shards balanced at 49% / 50%, auth_failed zero for the whole run, and no cores or invariant failures on any of the nine hosts.

  5. Phase 5Aug 10 – Aug 18

    Benchmark campaign — 175 runs at 1, 2 and 4 shards

    Built a repeatable harness (one run per configuration, automatic collection, verdict, and analysis) and swept shard count, executor count, cache size, batch size, and workload shape. This is what produced the performance and capacity answers below — and four more bugs, none of them sharding's.

Results

What the numbers actually say

Sharding is a capacity win, not a throughput win. That is the honest headline, and it is worth stating before anyone reads a tx/s figure the wrong way.

Throughput is flat, then declines. Splitting a block into phases explains why: commit gets 24% faster with shards (2,194 → 1,666 ms) while nomination gets 61% slower (1,352 → 2,180 ms) and swamps the gain. Nomination is where the scheduler does its per-address hog-age reads. The batched scatter-gather is correct — one RPC per shard, not one per account — but it waits for the slowest shard, so its cost grows with shard count. That is the specific engineering target if sharding throughput matters.

Caveat that bounds every capacity number

The mempool holds at most 5,000,000 pending transactions and silently discards the rest (a hardcoded constant with an existing TODO asking for it to be a flag). Offering 1.3 billion transactions committed only 78.8M. Raising that constant is the prerequisite for any large-capacity demonstration — but not before the detached-coroutine guard lands, because a 50M backlog reaches 41.8 GB of mempool RSS and 252 MB database messages, which is where issue #10 bites.

Side effects

Sharding was a load-bearing test of main

Ten issues are written up with repro steps and artifacts. Most of them are not sharding bugs — they are pre-existing assumptions that only break when something exercises them. Sharding was the first thing to do so.

Two findings worth escalating beyond this project

  • A failing CHECK in a Release build is undefined behavior. Under NDEBUG, x23::panic compiles to std::unreachable(), so a failing CHECK at -O3 became a SIGSEGV with no CHECK FAILED line and a garbage backtrace. It cost days on a 37 GB core to establish that a clean assertion failure was hiding behind a segfault. This applies to every CHECK in every Release binary we ship.
  • An unguarded co_await in a detached coroutine is fatal to the process. On stream failure every in-flight call is handed an empty buffer; deserializing it throws, and a detached coroutine with no handler terminates. Three separate call sites have now killed the mempool this way.
  • Release builds in this tree were not NDEBUG. A vendored dependency does add_definitions(-UNDEBUG) for every non-Debug build, and it lands after the release flags on the command line. Every performance number measured from this build directory before August 10 was assertion-enabled.

Remaining

What is not done

  • Protocol reconciliation (merge blocker). The ShardCard identity fields sit on an interim protocol branch; they must land on protocol main and propagate through groundhog-go before this PR can merge.
  • Viewing snapshots. Snapshots open on the primary shard only, while snapshot-scoped reads route by address to the owner. Latent today because the read path is unexercised; the fix is to open on every shard and thread one id per shard. This is the largest remaining piece of design work.
  • A keyed routing hash. FNV-1a is unkeyed and therefore grindable. Replacing it needs a key that survives restarts — and it gets harder the more data exists on disk, so it should not wait long.
  • Commit atomicity. Commit still fans out non-atomically. Partial commit is detected at startup, not prevented.
  • The nomination path. Per-address hog-age reads are the reason throughput doesn't scale. Named target, not yet worked.
  • Scale. Unit-tested at N = 2, 4, 8 and benchmarked at 4; the long clean correctness runs are all at N = 2.

If you remember five things

The short version

  1. 01

    The database is now N processes, and the block header does not know it. LtHash16 additivity makes shard count a local deployment decision rather than a protocol change.

  2. 02

    One routing rule, one implementation, shared by the mempool, executor, and auth paths. Identity is persisted, declared, and fail-stop at every seam.

  3. 03

    Fan-out has a discipline — launch all, drain before rethrowing, visit every shard. Each of those three rules is a bug that actually happened.

  4. 04

    Validated on a 2-shard cluster: 79.5M transactions, 343 non-empty blocks, shards balanced 49/50, zero cores and zero invariant failures. Then 175 runs at 1, 2 and 4 shards to find out what it buys.

  5. 05

    What it buys is capacity, not speed: every sharded capacity run finished where the unsharded ones stalled, while throughput stayed flat because nomination got slower as commit got faster. And along the way it surfaced ten issues, most of which were sitting on main, invisible.
