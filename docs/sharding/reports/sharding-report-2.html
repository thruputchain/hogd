What sharding does and does not buy hogd

Three questions, measured on the hog cluster over 2026-08-17 and 18: what shard count does to throughput at the default workload, what raising the mempool transaction limit costs, and what happens when database writes rather than transfers dominate a transaction. Short answers: nothing, more than it buys, and it is the one case where sharding scales.

Committed counts come from chuckd's per-block record, not mempool_commit_removed_tx_count, which charges a full 1M per commit whatever the block held and overstated the 75 GB arms by 3.4x. Cells marked CI ran against a competing job on shared hosts and are floors, not measurements.

Read the rows, not the columns. The executor count at which throughput saturates rises with shard count. One shard is done at two executors — 197,986 then 195,945, no gain from a third. Three shards is still climbing at three: 173,831 → 193,405 → 212,517, +11% then +10%. Sharding fans execution work outward, so a sharded configuration needs more executors to reach the same ceiling, and the single-executor column shows the cost of not providing them: 178k, 181k, 174k, 156k as shards go 1, 2, 3, 4.

So "sharding does not improve throughput" holds only when execution capacity is already adequate for the shard count. It is a statement about this cluster's executor provisioning, not about sharding. Three shards routes evenly — h % shard_count is a true modulo, occupancy measured at 11%/11%/11% and 9%/10%/10% — so nothing here is an artefact of a non-power-of-two layout. The empty cell is 4 shards with 3 executors: at four shards the databases take hog1/hog2/hog3/hog11 and every other host runs a service, so a third executor would have to share one and confound the comparison. The cluster is one machine short.

Write-heavy ladder — state created by the workload

75 GB of cache per shard, and every work transaction writing 16 KiB of contract storage through the real execution path (storage_filler, 256 instances so the state spreads over shards instead of pinning to the one address that owns a single contract). This is the first configuration whose per-transaction cost is dominated by database writes rather than token transfers — and the only one in which throughput rises with shard count.

It is not a memory-capacity result. Resident memory was ~10.5 GiB in all three arms (15% of a 69.85 GiB cache at one shard; 7+3+3+2% at four), because the filler's writes are never read back and the ramdb passes them through to disk. The extra cache the sharded arms have is never demanded. What scales is the write path: per-host disk footprint falls 105 → 62 → 32 GB while throughput rises.

What this campaign added

Raising the mempool limit costs throughput and buys almost no commits

Matched pairs: 2 shards -36% tx/s / +5% committed, 4 shards -36% tx/s / +3% committed, 1 shard -12% tx/s / -12% committed, 2 shards -6% tx/s / -14% committed, 4 shards +6% tx/s / -15% committed. The limit gates the pending backlog, not a run's lifetime total, so on a long run the surplus becomes backlog rather than commits — and a scheduler holding tens of millions of entries is slower to nominate. Two independent shard counts landing on the same throughput loss is what makes this a real effect rather than cluster contention, which was my first reading when only one arm showed it.

Sharding does scale throughput -- once the database is the bottleneck

The crossover ladder above is the only configuration in this campaign where throughput rises with shard count: 51,054 -> 65,242 -> 73,880 tx/s at 1, 2 and 4 shards, committing 33.4M / 38.0M / 39.7M. The difference is what a transaction costs: the transfer workloads write ~392 bytes of state each and never stress the database, so shards only add coordination; a filler transaction writes 15,284 bytes (measured), the database becomes the constraint, and splitting it is what helps. What it is not: a memory-capacity win. Resident memory was ~10.5 GiB in every arm — the filler keys each write from its own transaction nonce, so nothing is ever read back and the cache passes writes through to disk. The 1-shard arm put 105 GB on one host's disk while holding 15% of its cache; four shards put ~32 GB on each. So this measures write-path parallelism, and the read penalty of a working set outgrowing memory remains unmeasured. And the arms are matched on offered load and duration, not on final state: more shards commit more, so they accumulate more.

With the database idle, sharding buys no throughput

At the old limit 2 and 4 shards committed identically and 4 shards was marginally slower. The raised limit moves both arms down together rather than changing their ordering. State in these ladders is 8–31 GB, well inside one shard's cache, and each transaction writes ~392 bytes — so they measure sharding's coordination cost with none of its benefit. Read them as the floor case, not as a verdict on sharding.

A counter in the earlier analysis overstates commits 3.4x

mempool_commit_removed_tx_count equals blocks committed × kMaxBlockSize + genesis in every run measured — it charges a full 1,000,000 per commit whatever the block actually held, and blocks are usually far from full. It reads 269M against chuckd's 78.8M on 1shard-75gb-01. Every figure here uses chuckd's per-block sum, which the state size corroborates at ~392 B/tx.

A filled 300 GB shard fits only one machine in this cluster

hog1 has 755 GB; the other ten hosts have 377 GB. The ramdb needs headroom above --ram-bytes for compaction and disk buffering, so hog2's hogdb died with still out of memory; compacting all loglets partway through a 300 GB fill that hog1 completed. Filling even hog1 to 90% left it compacting continuously. A uniform ladder therefore tops out at 200 GB per shard, filled to ~70%.

State cannot be injected into a sharded database

Writing synthetic items straight into each shard's ramdb fills a large cache in minutes instead of ~10 hours, and it works at one shard. It cannot work at more: each shard's pre-genesis content differs, so their genesis hashes differ and the mempool refuses to start on db shard tip divergence. Only kHogAge and kGlobalMetadata escape the consensus hash, and hog-age rows are fixed ~100-byte records — 700M of them to fill 141 GB, back inside the per-item cost collapse. Replicating identical items on every shard would keep the hashes equal but break the invariant that each item is hashed on exactly one shard, describing a database that cannot exist.

hogdb dies silently mid-run, and the harness cannot see it

Three arms tonight ended with hogdb gone: its last log line is a successful committed block, then a multi-GB core and no error, with ample free memory. The mempool survives, so run-one.sh — which decides liveness from pgrep mempool_exec — kept polling a dead run until its stall timer expired. All three were at the 50M limit with tens of GB of backlog, while every arm at the old limit completed; not conclusive, since one 50M arm did finish, but it is the pattern to chase. The watcher now checks every shard host and kills a dead arm in ~6 minutes.

Preload throughput collapses as the database grows

Writing 4 KiB items ran at 2.3 GB/s into an empty database and 64 MiB/s by 33M items — a 35x decay driven by per-item cost, not by disk (the device was idle) or memory. Using 32 KiB items needs 8x fewer inserts for the same bytes and holds ~1 GB/s, which is what made a 269 GB fill take 282 s. The same write path serves genesis, so a large account count will meet the same wall.
