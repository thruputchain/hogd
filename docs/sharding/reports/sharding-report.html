Throughput does not scale with shard count

Adding database shards does not add throughput, and by four shards it costs a little. Across 7 runs that completed on a quiet cluster:

shardstx/sruns vs 1 shardshare of linear scaling
1211,1822+0.0%100%
2214,3252+1.5%51%
4196,9853-6.7%23%

Linear scaling would mean N shards deliver N× the throughput of one. The measured share falls from 51% at two shards to 23% at four — the hardware doubles, then doubles again, while throughput stays flat and then dips. That is the signature of a system whose limit lies somewhere other than the database: dividing the database adds coordination cost without removing the constraint.

Under real memory pressure, sharding is the difference between finishing and failing

19.3 GiB7.3 GiB2.0 GiB33,000,000 stalled at 78% — mempool aborted
218.6 GiB10.5 GiB8.1 GiB40,500,000 completed
437.3 GiB11.1 GiB26.1 GiB39,000,000 completed

Every other measurement in this report was taken with the working set at 8–27% of a single shard's memory, so the capacity sharding adds was never used. These runs use --num-virtual-accts, which pays transfers to synthetic recipients that nothing is deployed at, so each first payment inserts a new item and state grows with the transaction count. Two runs per configuration.

Both unsharded runs failed and every sharded run finished. At one shard the cache reached 78% and the mempool aborted (terminate called without an active exception) after 33M transactions. Two and four shards carried 39–41M and completed with 8 and 26 GiB spare.

Block commit time under this pressure, over the same matched window (1,000,000-tx blocks): 1 shard 5.39 s median (mean 5.93, p90 7.54), 2 shards 5.75 s (6.17, 7.76), 4 shards 6.14 s (6.59, 8.27). The same mild per-block cost as everywhere else in this report — sharding buys the ability to finish at all here, not faster blocks.

Read the workload figures as a floor, not a ceiling: the sharded runs stopped because the coordinator finished submitting, not because they ran out of memory, so 1.23× is the least they could carry rather than the most. Capacity itself scales exactly 2× per shard; how much workload that converts to has not yet been measured to the limit.

Memory capacity does scale — exactly 2× per shard

Each shard runs with --ram-bytes 10000000000, which hogdb reports as a 9.31 GiB cache, so total in-memory capacity is 9.3, 18.6 and 37.3 GiB at one, two and four shards. This is the one dimension where sharding delivers its full promise, and it is measured rather than assumed: the same working set occupies 27% of the cache on one shard, 13–14% on two and 8% on four — halving each time the shard count doubles.

The 10 GB figure is a hardcoded flag, not a limit. These hosts have 377 GB of memory with 336 GB free, so each shard is using 2.7% of its machine and the setting could be raised by an order of magnitude. Note the corollary: at 27% utilisation on a single shard, this workload never comes close to exhausting memory, which is why the extra capacity buys no throughput here. Demonstrating a memory benefit needs a working set larger than one shard can hold.

Sharding adds work the executors must absorb

1207,948189,390156,428
2211,182214,325196,985

With one database there is almost nothing for a second executor to do: 207,948 tx/s against 211,182, a 1.5% gap. By four shards the gap is 21%. Neither arm ever gains from sharding, but an under-provisioned executor tier makes the penalty about three times worse — throughput falls 25% from one to four shards on a single executor, against 7% on two. So sharding creates work the executor tier has to absorb, and part of the cost measured elsewhere in this report is provisioning rather than anything inherent to sharding.

The typical block gets steadily slower — the other side of the missing throughput — while the tail gets faster: p90 falls from 9.0 s to 5.8 s. Spreading work over more databases smooths out whichever single shard would otherwise straggle, so the body of the distribution tightens even as its centre moves the wrong way.

Smaller batches: 100,000-transaction submissions

1 DB shard (unsharded)2 DB shards4 DB shards

Throughput here is capped by the harness, not by hogd: chuckd waits at least a second between submissions, so the ceiling is ~100,000 tx/s and the database idles between batches (median submit call: 92 microseconds). Both configurations sit against that ceiling. Measured over blocks 1–110 of each run, so run length cannot influence it.

These rates are far below the block times below would imply, because block duration is heavily skewed: the mean is 3.4× the median (median 1.2 s, p90 ~9 s, worst 23 s). Total throughput follows the mean and so is dominated by the slow tail; the median describes a typical block. The two measures disagree in direction, and both are reported rather than picking the flattering one: 1 shard has the faster typical block (−9.6% median), 2 shards the slightly better tail, and overall throughput is a wash.

What these numbers are not

They are not sustained throughput. The offered rate exceeds capacity, the backlog grows, and the coordinator stops after its last batch — so no run reaches equilibrium. Second-half rates of 168–186k tx/s are closer to the sustainable figure and still falling. Establishing the steady state needs a longer run at an offered rate just above capacity.

They are valid for comparing shard counts, which is what they are used for here: both configurations were measured over identical windows of an identical workload.
