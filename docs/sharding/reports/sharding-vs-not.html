Does sharding help hogd?

Eleven runs of the same workload — 100 batches of a million transactions, 10 GB of cache per database shard — across one to four shards and one to three executors. Throughput is the matched-block-window figure, because both throughput and block time decay within a run and whole-run averages cannot be compared across runs of different length.

Sharding does what it is meant to do at the database: block commit gets 45% faster from one shard to four. It is paid for almost exactly by nomination, which gets 80% slower over the same range. That cancellation is the whole story of the flat throughput curves below.

Does sharding change the cost of a read?

Average memory access time, measured with the database's own read benchmark on the path hogdb uses. The classic form is hit time + miss rate × miss penalty; here the miss term is zero because Database::get consults an in-memory hash map and nothing reads from disk on a lookup. So AMAT is the hit time, and the question is whether shard size or shard concurrency moves it.

Two consequences worth carrying. Every item hogdb serves is in RAM, so a shard's capacity is its memory and there is no cache-miss cliff to design around — but equally no graceful degradation, which is why a cache smaller than the working set kills the process with out of loglet memory rather than slowing down. And since reads cost the same whatever a shard holds, the read-side case for sharding rests on aggregate memory and on spreading concurrency.

Sharding with consensus taken out

The same question asked of the execution path alone. multiexec_runner replaces the mempool, chuckd and scpd with a mock scheduler that opens a block, hands one million transfers to the executors and closes it, so nothing here waits on nomination or on a quorum. Each cell is five trials of a one-million transaction block, and the executors sit on the same three machines throughout, so only the number of shards, the number of executors and the size of the account set change.

Two caveats belong with these numbers. The bench calls close_snapshot and commit_snapshot on each shard in turn where the mempool issues them together, so its per-block overhead grows with shard count in a way production's would not; the last column sizes that, and it is 2-5% of the measured slowdown. And ERC20 balances live under a single contract address, so even at 100,000 accounts the state is not evenly spread across shards -- which is the most likely reason four shards never pay for themselves here.

What sharding buys before the workload asks for it

hogdb holds its items in memory and has no read-miss path -- Database::get consults a hash map and nothing falls back to disk -- so the state a configuration can address is exactly the sum of its shards' budgets. Capacity is the one benefit of sharding that does not have to be earned as a rate: it is provisioned, and the only question is whether a run at that size works. Every column below is a run that completed.

The stock budget: 10 GB per shard

The default-workload arms as they have always been run. At this budget the proportion is honest to the eye: the workload holds a quarter of one shard's capacity, and adding shards dilutes that share rather than growing what is held.

The same workload at 300 GB per shard

Nothing about the load changed -- same transactions, same 10,000-account keyspace, no preload and no filler. Only --ram-bytes moved, from 10 GB to 300 GB, which puts a terabyte of capacity behind four shards and leaves the workload sitting in a rounding error of it.

What bounds a single shard is its host's memory, and --ram-bytes does not change that: the flag reserves address space, so an idle shard with a 256 GB budget showed 249 GB of virtual size against 25 MB resident, and each shard in the four-shard arm ran at 291 GB virtual against 2.3 GB. Only live items cost memory. A typical hog host has 377 GB and hog1 has 755 GB, so one shard tops out there however the budget is set -- which is why a terabyte cannot be held unsharded on this cluster, and what four shards are actually buying. Nor can the point be made from below: the 2 GB-per-shard arms crashed, because a budget too small for the working set exhausts the allocator rather than spilling (ISSUES #1).
